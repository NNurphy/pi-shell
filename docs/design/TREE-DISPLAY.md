# 会话树展示逻辑（TREE-DISPLAY）

> 配套：`docs/DESIGN-SYSTEM.md` §3.7 面板、`docs/design/LAYOUT.md` §5 面板布局
> 目标数据：单会话 **949 / 5000 节点**的线性长链 + 若干分叉（pi 的条目模型：`{id, parentId, type, timestamp, message}`）

---

## 0. 问题定义（先对齐"难在哪"）

pi 的会话是**单链表**：`id + parentId + leafId`（docs/03-design.md H-6）。这带来三个与"树"这个词不符的事实：

1. **"深度"≈"节点数"**。一条 5000 节点的线性会话，第 5000 个节点的深度是 5000。
   → 任何"按深度缩进"的树，在 5000 深度时会横向跑出屏幕。**缩进必须在 3 层封顶。**
2. **没有子节点索引**。`get_entries` 只给条目流，分叉点只能靠 `parentId` 反推（客户端建 `parent→children` 索引），展开整棵树需要额外数据。
   → 默认视图**不应**依赖完整树，只依赖"叶子 → 根"这一条链（一次取回即可）。
3. **用户在树里的真实需求只有三件事**：① 我在哪（当前节点）② 我这一路怎么走过来的（主干）③ 有没有别的岔路（分支数 + 从哪分出去）。
   → 树面板是"定位器 + 分叉入口"，不是"文件资源管理器"。

用户原话痛点：「信息密度高但是没有层级」「949 个节点不知道怎么翻」。所以设计的首要指标是**当前位置可辨识度**，不是"树画得全"。

---

## 1. 三个方案

### 方案 A · 主干优先 + 逐层分支折叠（Main path first）

**默认视图 = 当前叶子到根的主干一条线**，每个分叉点旁边放一个折叠行 `＋2 分支`，点击就地展开该分支（懒加载）。

```
会话树                                       962 节点 · 12 层 · 6 处分支
┌──────────────────────────────────────────────────────────┐
│ [搜索节点…]                        只看分叉点 ☐   定位当前 │
├──────────────────────────────────────────────────────────┤
│ 12:20  ○ 你   现在信息密度高但是没有层级…        D000     │
│        ◇ 思考 4.1s                                        │
│ 12:21  ▸ bash git status --short        0.4s ✓   D002     │
│       ┃ ＋2 分支 · 从「先看数据」起                       │
│ 12:26  ◆ pi 先把树的设计定下来…                D003     │
│ 12:41  ▸ read docs/03-design.md         18ms ✓   D004     │
│ 12:58  ◆ pi 三条原则：结构先于装饰…            D1200    │
│ 13:02  ▸ bash rg -n "TODO" web/src     1.2s ✕    D4999 ● 当前 │
└──────────────────────────────────────────────────────────┘
```

**规则**

| 项 | 规则 |
|---|---|
| 主干来源 | `/api/session/tree`（已存在）返回的 `tree + leafId`；从 leaf 沿 `parentId` 回溯到根，**倒序**渲染（时间正序） |
| 行内容 | `时间(11 等宽) · 类型符号 · 摘要(单行 40 字省略) · 耗时/工具名 · 深度徽标` |
| 深度徽标 | `D0000`–`D4999`，等宽 10px，`--ink-3`；**只在 depth > 3 时显示**（浅层靠缩进已可读） |
| 缩进 | `min(depth,3) × 12px`，**上限 36px**；超过 3 层的行改为"悬挂态"：左侧一条 1px 虚线导轨 + 徽标承担深度信息 |
| 分支折叠行 | 每个 `children.length > 1` 的节点下方插一行：`┃ ＋N 分支 · 从「<该节点摘要 12 字>」起`，行高 28，背景 `--surface-hover`，`＋` 为 `--accent-ink` |
| 展开分支 | 点击后就地展开（缩进 +12）：先出 **12 行** + `继续加载这层（还有 N 层）`；分支尾部是该分支自己的 leaf，标 `分支末端` |
| 折叠 | 再点一次收起；`Esc` 收起最近展开的一层 |
| 跟随 | 默认跟随当前 leaf（打开即滚到叶子并高亮）；手动滚动后顶部出现 `↓ 定位当前`（`--accent-ink`），点击回跳 |
| 过滤 | `只看分叉点` 开关：隐藏非分叉节点，只留分叉点与叶子（5000 节点 → 通常 ≤20 行），这是**长会话的逃生舱** |
| 搜索 | 顶部输入框：匹配摘要/命令/工具名，命中行高亮 `--accent-soft`，`↑↓` 在命中间跳转，`Enter` 定位（自动展开其祖先链），`Esc` 清空 |
| 分叉入口 | ① 树内：任意节点 hover → `⋯` → `从这层新开分支`；② 会话流内：消息元数据行右侧 hover 出现 `分支` 按钮（见 §3）；③ 面板头：`克隆当前会话` |

**性能**：5000 节点也只渲染主干（≤5000，但虚拟滚动后 DOM ≤ 300 行）+ 已展开分支。首屏无额外请求。

---

### 方案 B · 缩略图 + 详情（Minimap + Inspector）

面板顶部一条 **24px 高的"深度带"**：横向 = 时间，纵向 = 分支路数，每个节点 1px 刻度；下面是**当前选中节点**的详情卡（摘要 + 前后 2 节点 + 操作）。没有完整列表。

```
深度带  ▁▂▃▅▇█▇▅▃▂▁▂▄▆█  ← 24px，可拖动 scrub
──────────────────────────────────
选中节点 #4820  D4820  ◆ pi
  「缩进上限应该设在 3 层，第 4 层用徽标…」
  ↑ 上级（#4819 工具 bash 1.2s）
  ↓ 下级（#4821 你：那分支数怎么显示？）
  [从这条新开分支] [在会话中查看]
```

- 优点：5000 节点下"全局形状"最强，DOM 极轻（canvas 一根带子）。
- 缺点：**精度低**——在 24px 高、5000 刻度的带子上点不中特定节点；分叉只能看到"鼓包"看不到内容；要"连续读一条路径"得上下来回跳；移动端 scrub 与滚动冲突；实现需要额外布局计算（分支 lane 分配）。

---

### 方案 C · 分页完整树（Paginated full tree）

完整树 + 按深度缩进 + 分页（每页 100 行）/ 或虚拟滚动 + 横向滚动。

- 优点：信息最全，所有分支同时可见；实现最"标准"（就是一棵树）。
- 缺点：**5000 深度直接击穿布局**——缩进 12px × 5000 = 60000px 宽，只能横向滚动；分页切断路径连续性（第 3 页看不到第 1 页的祖先）；"我在哪"依然要靠额外标记；移动端完全不可用。

## 2. 取舍表与选择

评分：5 = 最好，1 = 最差（针对 pi-shell 的单人重度使用场景）

| 维度 | A 主干优先 | B 缩略图+详情 | C 分页完整树 |
|---|---|---|---|
| **当前节点可辨识度**（核心指标） | **5** 叶子高亮 + 定位按钮 + 轴线连续 | 3 只能靠 scrub 位置 | 2 分页后丢失上下文 |
| 5000 节点性能 | **5** 首屏只渲染主干，DOM ≤300 | **5** canvas 单带 | 2 需要虚拟化 + 横向滚动 |
| 分支可发现性 | **4** 分叉点显式计数行 | 3 只见"鼓包" | 5 全可见 |
| 路径连续性（读"这一路"） | **5** 一条线读完 | 2 需上下跳 | 3 分页切断 |
| 搜索 / 定位 | **5** 列表内命中 + 祖先自动展开 | 3 命中后只能看详情 | 4 |
| 分叉操作（fork） | **5** 节点 hover / 消息 hover / 克隆三入口 | 3 详情卡单一入口 | 4 |
| 移动端可用 | **5** 单列表 + 44px 行 | 1 scrub 与滚动冲突 | 1 横向滚动 |
| 实现成本（人日） | 3 天（虚拟列表 + 展开状态机） | 5 天（lane 布局 + canvas + 手势） | 3.5 天（树 + 分页） |
| 数据依赖 | 只需 tree（现有） | tree + 分支 lane 计算 | tree + 全量子节点索引（桥需扩展） |

### 选择：**方案 A**，并把 B 的"形状感"作为后续可选增强（不是现在）

**理由（按权重）**

1. **它直接命中"我在哪"**。用户抱怨的不是"树不够全"，而是"翻不到当前在做什么"。主干一条线 + 叶子高亮 + `定位当前`，是唯一能 1 秒回答这个问题的结构。C 的完整性反而是噪音源。
2. **它与 pi 的链表结构同构**。主干 = 从 leaf 回溯 parent 链，**一次请求、零额外索引**；C 需要桥新增"取整棵子树"能力，B 需要客户端算 lane 布局。A 是唯一"今天的数据就够"的方案。
3. **5000 节点下它是唯一自然的**。深度 = 节点数这个事实，让"缩进表达结构"的方案（C）从根上失效；A 用**徽标承担深度、缩进只表达"层"**，绕开了这个死结。
4. **移动端不需要第二套逻辑**。A 就是一张列表；B/C 都需要移动专属手势或横向滚动。
5. **它的成本中位、可增量交付**：第一版可以不做虚拟化（主干 ≤ 5000 行，用 `content-visibility:auto` 先顶），第二步再加窗口化。

**接受的代价**
- 看不到"全貌"：多分支的拓扑形状不可见。缓解：折叠行显示分支数，`只看分叉点` 视图给出"分叉清单"（近似全貌）。
- 展开分支是就地插入，读的时候会出现"层级跳变"。缓解：分支行用虚线导轨 + 缩进 12px + 徽标明确标注 `分支`。

**为什么不现在做 B**：它是"看形状"的工具，不是"找位置"的工具；在还没有真实 5000 节点使用数据前，为形状投入 canvas + 布局引擎风险高于收益。留作 v2 的 16px 深度带回填（面板头一行，不影响列表）。

## 3. 分叉入口的位置与命中区

| 入口 | 位置 | 桌面命中区 | 移动 |
|---|---|---|---|
| 树内节点 | 行右侧 `⋯`（hover / 选中常显） | 28×28 | 行本身 44 高，长按出动作表 |
| 会话流消息 | 该轮元数据行最右 `分支` | 文本按钮，高 24 + 4px 外扩 = 32 | 长按消息 → 动作表 `从这条分支`（44 高） |
| 面板头 | `克隆当前会话` | 高 28 | sheet 头右侧 |
| 键盘 | 焦点在某轮时按 `F` | — | — |

分叉后的行为（与现有实现一致，仅调整提示）：在树中"从这层新开分支"→ 该节点成为新 leaf → **新分支出现在同一会话树里**；`克隆当前会话`→ 生成新会话并切到第 N+1 列（多列模式下不打断当前列）。

## 4. 懒加载策略（实现契约）

### 4.1 数据分三级

| 级 | 内容 | 来源 | 何时 |
|---|---|---|---|
| L0 | 主干（leaf→root 全链） | `GET /api/session/tree`（现有，`{tree, leafId}`） | 打开面板时一次 |
| L1 | 分叉点及其**子节点计数** | 由 L0 数据 + `parentId` 反推（需桥在 tree 节点上补 `childCount`，1 行改动） | 随 L0 |
| L2 | 展开某分支的子链 | **待加**：`GET /api/session/tree?root=<id>&depth=1`（或复用 `get_entries` + 客户端切片） | 点击折叠行时 |

> 桥的接口是**唯一实现依赖**：`childCount` 与 `root/depth` 参数。若不想动桥，退化方案 = 一次性取 `get_entries` 全量（5000 条约 3–8MB），客户端建索引——不推荐，但可用。

### 4.2 展开状态机

```
collapsed ──click──> loading ──ok──> expanded(12 行 + 更多)
   ^                    │                │
   │                    └─error─> error(行内重试, --danger)
   └──────── collapse / Esc ◀───────────┘
```

- **请求去重**：`inflight: Map<rootId, Promise>`，重复点击复用。
- **缓存**：`childrenCache: Map<entryId, Node[]>`，上限 200 项（LRU），关闭面板不清（同一会话内有效），切会话清空。
- **取消**：关闭面板 / 切会话 → `AbortController.abort()`，丢弃结果（避免把旧会话的行插进新会话）。
- **分块**：每个分支首次 12 行，`继续加载` 每次 +50 行（不一次渲染 5000 行）。
- **虚拟化**：列表窗口 40 行 overscan；行高固定 28（紧凑 24）才能用固定高度虚拟滚动——这是选择"单行摘要"而非"多行卡片"的另一个理由。
- **无障碍**：展开行 `aria-expanded`，`↑↓` 移焦点，`→` 展开，`←` 收起。

### 4.3 性能预算

| 指标 | 预算 |
|---|---|
| 面板首开（5000 节点主干） | ≤ 120ms 到可交互 |
| 同时 DOM 行数 | ≤ 300 |
| 单次展开请求 | 1 次，≤ 80ms（本地桥） |
| 折叠点计数计算 | 一次性 O(n)，≤ 10ms（5000 条） |
| 内存（索引） | ≤ 8MB |

## 5. 搜索与定位

- 搜索范围：**已加载节点**（主干 + 展开的分支），命中的祖先链自动展开。
- 结果条：`3 / 17 命中`，`↑` `↓` 切换，`Enter` 定位（滚动 + 高亮 1.2s 淡出）。
- 深链：会话流每一轮有锚点 `?session=<id>#t=<entryId>`；从树里 `在会话中查看` 直接跳该锚点。
- 空结果：`没找到包含「xxx」的节点` + `清除过滤`（`--ink-3`，不弹框）。

## 6. 视觉规格（与设计系统对齐）

| 元素 | 规格 |
|---|---|
| 面板宽度 | 340（桌面停靠）/ 全屏 sheet（移动） |
| 面板头 | 36px：标题 13/600 + 右侧 `×` 32×32 |
| 统计行 | 32px：`962 节点 · 12 层 · 6 处分支`，等宽 11 `--ink-3` |
| 搜索行 | 36px：输入高 28，`--line-control` 边框，聚焦 `--accent` + 2px 软环 |
| 节点行 | 28px（紧凑 24）：时间 44px 等宽 + 类型符号 12px + 摘要 flex + 耗时 44px 右对齐 + 深度徽标 40px |
| 类型符号 | `○` user / `◆` assistant / `◇` thinking / `▸` tool / `!` error（**单色** `--ink-3`，不按类型着色） |
| 当前叶子 | 行底 `--accent-soft` + 左 2px `--accent` + 右侧 `当前` 11px 等宽 |
| 分叉折叠行 | 高 28，底 `--surface-hover`，左 1px 虚线 `--line-strong`（悬垂导轨），`＋N 分支` 用 `--accent-ink` |
| 分支缩进 | 展开层统一 +12px（**不再按深度**），悬挂导轨表示"这是另一条线" |
| 长按/选中 | `--surface` + 左 2px `--accent` |
| 滚动 | `scrollbar-gutter: stable`，滑块 10px `--line-strong` |

**不做**：曲线连接线（SVG 贝塞尔）、节点卡片、迷你地图缩略画（v2 再说）、按类型给彩色圆点。

## 7. 三种方案的"如果选它们，页面会长什么样"

为便于拍板，附一句话画面描述：

- **A**：一张 28px 行的清单，一列纵深，末端一个高亮"当前"，中间夹着几条 `＋2 分支` 的折叠条。像 git log 的一列（但带分支计数）。
- **B**：面板上半是一条 24px 的密度带（像音频波形），下半是一张"节点详情卡"，上下切换靠点带子和方向键。
- **C**：一棵每层缩进 12px 的树，5000 深度时占宽 60000px，横向拖到底才能看到叶子；分 50 页。

## 8. 第二阶段落地顺序（建议）

1. `childCount` 反推 + 主干渲染 + 叶子跟随（纯前端，1 天）
2. 分叉折叠行 + 就地展开（需桥加 `root/depth`，0.5 天桥 + 1 天前端）
3. 虚拟化 + `只看分叉点` 过滤（0.5 天）
4. 搜索 / 定位 / 深链锚点（1 天）
5. 分叉入口统一（树 / 消息 / 克隆，0.5 天）

## 9. 待决

1. `＋N 分支` 展开后是否需要"该分支的末端预览"（多一次请求）？
2. 树面板是否需要"时间轴渐变"（按时间淡出越早的节点）？——本方案**不做**，会与深度徽标抢注意力。
3. 分叉后是否自动把新分支列到"多列"里（当前建议：不自动，只开在当前列）。
